- **The "unparsed-line rule", as SPEC §2.3 states it (SPEC.md:176-185).**
  - `.headers.raw` is decoded as Latin-1 and split on CRLF only.
  - The first line is the request line: method and path.
  - A later line is a header if the text before its first colon is a non-empty token. Its value has surrounding SP/HTAB removed; any bare CR or LF inside stays.
  - Every other non-empty line is listed verbatim under `unparsed`, which is absent when empty.

  **Judgement: sound for header lines, with one hole.** On 16 head shapes the rule behaved as follows:
  - Obs-fold continuations, a line with no colon, `: v`, `Name : v` and non-token names all land in `unparsed`.
  - Bare LF and bytes ≥0x80 are kept, and an empty value is `""`.
  - Trimming is not "improving" the record: RFC 9110 says that whitespace is not part of the value, and `.raw` is the record.

  **The hole is the request line.** Whatever follows the path (the HTTP version, or anything else) is dropped without being listed. An LF-only head yields `headers: []`, no `unparsed` and `content_type: null`, so the json omits things without saying so (F-c1). Keep "absent when empty" once that is fixed; until then, absence falsely implies that everything was parsed.

  **The rule was set by the batch and deferred to review instead of halting** (CLAUDE.md halt point: "a rule … SPEC.md does not already state"). A0c, in the same run, did halt. Z4's sealed `headers.json` will carry this rule for good. → **Z-1**.

Thread: the fixture's `collector.log` is on the Collector's own wall clock (`19:20:46+0300`), not the "chosen clock 09:00:0N" the commit body describes for the capture.
